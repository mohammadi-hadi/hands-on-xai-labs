## Exercise 4.1: Reproduce the validation/test collapse yourself *(warm-up)*

**Goal.** The ledger's headline: the same specimen scores macro-F1 0.676 on the `tweet_eval/hate` VALIDATION split but 0.357 on TEST, with the hate-prediction rate jumping from 61% to 96%. Reproduce both halves so you never trust a single split again.

**Steps.**
1. In the evaluation cell that scores 500 validation tweets, duplicate it for 500 test-split tweets (`load_dataset("tweet_eval", "hate", split="test")`).
2. Print accuracy, macro-F1, and the fraction of tweets predicted hate, side by side for both splits.
3. Read 5 test tweets the model calls hate with p > 0.9; note the immigration-hashtag pattern.

**Hint.** This is inference only (no retraining), so it works identically with the committed `models/ch04-specimen` and is cheap on CPU.

**Solution sketch.** Copy the eval loop, swap the split, print a 2-row table. With the book's specimen you should see roughly val 0.676 / test 0.357 macro-F1 and a ~96% test hate rate (exact reproduction requires the committed checkpoint; a self-trained specimen will differ because of MPS nondeterminism). This is the known SemEval-2019 Task 5 test-split topic shift, and it is why every later chapter (5, 6, 8) samples from validation only.

## Exercise 4.2: Does SHAP's saturation point move with input length? *(core)*

**Goal.** The ledger measured that on a 21-token tweet the partition masker saturates: 512 and 1024 `max_evals` both cost 0.41 s; extra budget buys nothing. Test the natural hypothesis the chapter leaves open: the saturation point should grow with token count.

**Steps.**
1. Find the runtime-curve cell (it sweeps `max_evals` for one tweet).
2. Pick three inputs of different lengths: roughly 10, 20, and 40+ tokens (concatenate two tweets for the long one).
3. Sweep `max_evals` over `[64, 128, 256, 512, 1024, 2048]` for each; record wall time *and* the top-5 token ranking at each budget.
4. Plot one runtime curve per length; mark where the ranking stops changing.

**Hint.** Saturation has two signatures: flat cost AND frozen rankings. Check both: cost can flatten while attributions still shift slightly.

**Solution sketch.** Nest the existing timing loop in a loop over the three texts; store `(length, evals, seconds, top5)`. The ledger pins one point: ~21 tokens saturates near 1024 (0.41 s flat). The other lengths are not in the ledger. Record what you find and compare against the chapter's number. The production takeaway (Chapter 13 reuses it): the eval budget that is wasteful for tweets may be insufficient for documents.

## Exercise 4.3: A random-attribution control for the agreement heatmap *(stretch)*

**Goal.** The ledger reports method agreement τ(LIME,SHAP)=0.59±0.20, τ(LIME,IG)=0.43±0.13, τ(SHAP,IG)=0.51±0.16. Those look meaningfully positive. But positive compared to what? Add the missing null: a seeded random ranking.

**Steps.**
1. In the agreement cell (the 3×3 Kendall-τ heatmap over the 10 tweets), add a fourth "method": `rng.permutation` of each tweet's word indices, seeded per tweet.
2. Recompute the now-4×4 τ matrix (mean ± std over the 10 tweets).
3. Optionally add a fifth pseudo-method (LIME rerun with a different seed) to bracket the real methods between "pure noise" and "same method, new noise."

**Hint.** Kendall τ between a fixed ranking and a uniform random one is 0 in expectation; with ~15–20 words per tweet the per-tweet spread is wide, which is exactly the point of reporting mean ± std over 10 tweets.

**Solution sketch.** ~6 lines: generate one random score vector per tweet, append to the method dict, rerun the existing double loop. You should see roughly τ ≈ 0 (±0.2-ish) against the random row, comfortably below the 0.43–0.59 method-vs-method band, while LIME-vs-reseeded-LIME lands above it (the ledger's stability run found seed-to-seed τ 0.62 at 500 samples, 0.83 at 2000). Result: the methods share real signal but agree with each other barely more than each agrees with its own resampled self at low budgets. Chapter 8 turns this into a proper evaluation.
